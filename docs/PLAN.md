## 1. Цель и критерии

### SMART-цель MVP

> **К концу MVP (4–6 недель, 6 стадий) бот принимает боевые заказы:**
> - **S** — каталог (категории + товары с фото и ценами) → корзина → оформление (имя, телефон, адрес, время доставки) → подтверждение оператором → предоплата 50% через Kaspi (чек клиента) → статусы и история.
> - **M** — оформление ≤ 3 минут; заказ у оператора ≤ 30 секунд; 100% заказов доходят до оператора; 0 потерянных корзин при рестарте; uptime ≥ 99% за тестовую неделю.
> - **A** — одна кухня, предоплата вручную через Kaspi (чек-подтверждение), ручная диспетчеризация доставки.
> - **R** — закрывает реальный канал продаж без разработки сайта.
> - **T** — 6 стадий, каждая 3–7 дней, с проверкой владельцем на чекпойнтах.

### Критерии приёмки MVP (Definition of Done продукта)

- [ ] Пользователь видит каталог: категории, товары, карточка с фото/описанием/ценой.
- [ ] Пользователь собирает и редактирует корзину (добавить / изменить количество / очистить).
- [ ] Пользователь оформляет заказ: имя → телефон → адрес → желаемое время → комментарий; корзина проверяется на мин. заказ (20 000 ₸) и срок предзаказа.
- [ ] Оператор подтверждает заказ, назначает способ доставки и цену, отправляет реквизиты Kaspi; клиент присылает чек; оператор подтверждает оплату и запускает приготовление.
- [ ] Статусы: оформлен → ждём предоплату → подтверждён → готовится → в доставке → доставлен / отменён; пользователь видит статусы и историю.
- [ ] Крупные заказы (от 60 000 ₸ по умолчанию, настраивается) не принимаются менее чем за 24 часа до времени доставки; обычные — минимум за 2 часа.
- [ ] Админ управляет каталогом (категории, товары, цены, фото, скрытие, стоп-лист) без правки кода.
- [ ] Корзина и заказы переживают рестарт.
- [ ] Бот на VPS, автозапуск, ежедневные бэкапы БД; контрольный сценарий на 2 аккаунтах.

### Не-цели MVP

- ❌ Автооплата Kaspi по API (интеграция Kaspi Pay SDK) — фаза 2; в MVP предоплата подтверждается чеком вручную.
- ❌ Интеграция Яндекс.Доставки по API — оператор отправляет заказ в Яндекс вручную/через кнопку с ссылкой (фаза 2).
- ❌ Веб-витрина, веб-админка (SQLAdmin) — фаза 2.
- ❌ Мульти-ресторан — одна кухня/бренд.
- ❌ Промокоды, бонусы, рефералки, отзывы, аналитика — фаза 2–3.

## 4. Архитектура

### Принцип: слоёный монолит, один процесс

Тонкие Telegram-хендлеры → жирные сервисы в `core/` (не знают про Telegram) → данные в `data/`.

```
delivery-bot/
├── bot/
│   ├── handlers/            # start, common; дальше: catalog, cart, checkout, orders, admin
│   ├── keyboards/           # inline-клавиатуры
│   ├── middlewares/         # throttling → БД-сессия → регистрация пользователя (ошибки — снаружи)
│   └── texts/               # тексты RU (i18n — стадия 5)
├── core/                    # домен: constants (статусы), users; дальше: catalog, cart, ordering
├── data/
│   ├── models.py            # SQLAlchemy 2.0
│   ├── repos/               # (стадии 2+)
│   └── migrations/          # Alembic (0001 — полная схема)
├── config/settings.py       # pydantic-settings, .env
├── integrations/            # payments/ (фаза 2), delivery/ (фаза 3)
├── docker-compose.yml       # postgres + bot
├── Dockerfile
└── tests/                   # (стадия 5)
```

### Ключевые решения

1. **Корзина — в БД**: `UNIQUE(user_id, product_id)`, `CHECK(quantity > 0)`; переживает рестарты. FSM — только для checkout-диалога.
2. **Снапшоты цен и названий** в `order_items` — изменение каталога не трогает заказы.
3. **Заказ создаётся одной транзакцией** (очистка корзины + order + items + событие).
4. **Статус-машина с историей** (`order_events`):

```
created → awaiting_prepayment → confirmed → preparing → delivering → delivered
   └─────────────┴──────────────────────┴──────────────┘──→ cancelled (с причиной)
```

- `created` — оформлен; пользователь может отменить.
- `awaiting_prepayment` — оператор подтвердил, реквизиты Kaspi отправлены, ждём чек.
- `confirmed` — чек подтверждён; заказ в работе (готовим к выбранному времени).
- Пользователь отменяет только `created`; оператор — до `delivering` включительно.

5. **Предоплата всегда 50%**: считается при создании заказа (`prepay_amount`), реквизиты — это поле `payment_details`, отправленное оператором (`payment_method`: перевод / ссылка / удалённая оплата).
6. **Проверки при оформлении (Stage 3)**: мин. заказ 20 000 ₸; время доставки в часы работы; обычный предзаказ ≥ 2 ч; крупный (≥ 60 000 ₸) ≥ 24 ч; товары из стоп-листа отсекаются.
7. **Порядок middleware**: ошибки (самый внешний) → throttling → сессия БД → регистрация пользователя.

### Модель данных

`users` · `categories` · `products` (photo_file_id, is_available-стоп) · `cart_items` · `orders` (доставка, время, деньги, prepay, чек) · `order_items` (снапшоты) · `order_events` (история). Схема полностью описана миграцией `0001`.

### Флоу пользователя

`/start` → меню → корзина → «Оформить» (имя → телефон → адрес → время → комментарий) → сводка → заказ создан → ждёт подтверждения → получает реквизиты Kaspi → оплачивает → шлёт чек → статусы по мере приготовления → «Мои заказы» (история).

### Флоу оператора (группа Telegram)

Новый заказ (сводка) → [✅ Подтвердить] [❌ Отклонить(причина)] → при подтверждении: выбрать доставку (своя/Яндекс/самовывоз) + цену, способ Kaspi, отправить реквизиты → [💳 Оплата получена] → [👨🍳 Готовится] → [🚚 В доставке] → [✅ Доставлен]; отмена — с причиной в любой момент до доставки.

**Фаза 2:** **Telegram Mini App** — веб-каталог внутри Telegram (React/Vite + FastAPI-API поверх тех же core-сервисов; бот остаётся для Kaspi-чеков, уведомлений и чата; требует webhook + публичный HTTPS — тот же VPS со стадии 6) · Kaspi Pay по API либо Telegram Payments (проверить наличие KZ-провайдера) · веб-админка SQLAdmin (один FastAPI-бэкенд с Mini App и админкой) · зоны/авторасчёт доставки · промокоды · повторный заказ в 1 клик · webhook + Redis.

### Решение: Mini App — фаза 2, не MVP
