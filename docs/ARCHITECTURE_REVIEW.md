# ARCHITECTURE REVIEW — ревью архитектуры DeliveryBot (deepseek-v4-pro, 2026-08-28)

> Автономный обзор кода внешней моделью **deepseek-v4-pro** (гейтвей opencode.ai/zen/go/v1)
> по заданию владельца («полезное без вмешательства»). Ревью — рекомендации,
> решения принимает владелец. Ниже: вывод модели + короткие примечания DSH-партнёра.

## 1) Сильные стороны (подтверждены моделью)

- Чистое слоистое разделение: хендлеры → `core/` (без Telegram) → `data/` — легко тестировать и подключать новые каналы (Mini App).
- Детерминированный матчер заказов вместо LLM — нет галлюцинаций и лишних расходов.
- Статус-машина, транзакция при `create_order`, бизнес-правила в core.
- 65 зелёных тестов; изоляция core готова к фазе 2 без переписывания.

## 2) Риски и фиксы (с приоритетами)

### P0
- **Идемпотентность Kaspi-платежей** (для фазы 2): повторные webhook → двойные зачисления.
  Фикс: таблица `payment_events` с уникальным ключом `(external_id, type)`, `INSERT ... ON CONFLICT DO NOTHING`.
- **ПДн без регламентов** (телефоны, адреса): держать политику хранения, логировать без ПДн, при росте — шифрование.
- **Зависимость от провайдера LLM**: при недоступности гейтвея FAQ деградирует.
  Фикс (уже есть): фолбэк «напишите оператору» + `LLM_PROVIDER=mock` для отката; добавить мониторинг ошибок провайдера в логи.

### P1
- **In-memory история FAQ** теряется при рестарте → перенести в БД с TTL (таблица `ai_chat_history` + чистка по cron/при старте).
- **Ручная проверка чеков** — узкое место; фаза 2: QR/OCR с ручным подтверждением, пока — улучшить UX оператора (уведомления, быстрые кнопки).
- **Тесты на SQLite не покрывают PG-специфику** → добавить интеграционный прогон на PostgreSQL (можно на ВМ при деплое: `pytest` в контейнере).
- **Rate limit ИИ**: throttling есть на уровне Telegram-апдейтов; добавить пер-юзер лимит LLM-вызовов (счётчик в памяти/БД, например ≤30/час).

### P2
- **Мониторинг**: подключить Sentry (события ошибок) и базовые метрики; пока — регулярный просмотр `docker compose logs`.
- **Версионирование контрактов core** перед Mini App: Pydantic-схемы для API.

## 3) План фазы 2 (Mini App + Kaspi + webhook) — по шагам

1. **FastAPI рядом с ботом, long polling не трогаем**: те же core/services, эндпоинты `GET /menu`, `POST /orders`, `GET /orders/{id}`; initData-валидация (HMAC-SHA256 от бот-токена).
2. **Mini App (React/Vite)** — клиент к FastAPI; авторизация через initData; платёжный слой — Kaspi-ссылка/QR.
3. **Kaspi Pay Merchant API** отдельным модулем `integrations/kaspi`: sandbox → прод, webhook с идемпотентностью, обновление статусов заказов.
4. **Webhook вместо polling** — только когда всё выше стабильно; в отдельном окне обслуживания, с мгновенным откатом на polling; AI-бот продолжает работать в это время (или работает второй инстанс с тестовым токеном).
5. **Автораспознавание чеков** — полуавтомат: OCR подсказывает, оператор подтверждает.

Как не сломать прод: до шага 4 бот продолжает работать как есть; переключение на webhook — feature-flag/отдельное окно; тесты — тестовый бот @centerbyfoodplovtestbot.

## 4) Что НЕ делать (мнение модели, согласны)

- ❌ Микросервисы — монолит справляется; FastAPI и бот в одном процессе.
- ❌ LLM для критичных операций (расчёты, статусы, платежи) — только FAQ/советы.
- ❌ Полный автомат по чекам без ручного контроля на старте.
- ❌ Лишние слои абстракций (Repository и т.п.) без потребности.
- ❌ Долгое хранение чатов — чистить по TTL.
- ❌ Самодельная криптография для Kaspi — официальные SDK/стандарты.

## Примечания DSH-партнёра

- Пункты P0/P1 уже частично реализованы: фолбэк LLM, лимит токенов, эскалация человеку, откат `LLM_PROVIDER=mock`.
- Быстрый выигрыш до Mini App: персистентная история FAQ + пер-юзер лимит LLM (задачи на след. итерацию).
- Следующий шаг по плану — Mini App: владельцу нужен домен + HTTPS на ВМ.
